# Features and how each is checked

Every feature the owner can see, and what verifies it: the test suite on every change, the release
probe (`node probe/main.ts`, described in `CONTRIBUTING.md`) on every new
`@anthropic-ai/claude-agent-sdk`, and what nothing checks automatically. A new feature adds its row
in the same pull request. The Test suite column names the files under `test/` that cover a row, each
by its path from the repository root. The Probe column takes one of three forms: the claims of
`probe/claims.ts` that check the row (`P` ids for the features, `L` ids for a limit of
`docs/limits.md`); `n/a: <reason>` for a feature that does not rest on the SDK (Slack, the Home tab,
the daemon's own words, npm, the LaunchAgent); or `by hand: <why>` for one that rests on the SDK and
that a probe cannot see, which the probe prints in its checklist. A row rests on the SDK when what
it does depends on what the SDK or the CLI emits, accepts or lists. `test/probe/features.test.ts`
fails on a cell that is `none`, empty, a mix of the forms, a repeated id or a reason that names a
claim, on a claim that does not exist, on a feature claim that no row names, and on a row that names
a test file that does not exist. The Rests on column
names, in backticks, the SDK names (`Query.setModel`, `SDKTaskStartedMessage`) and `/commands` the
row depends on, and is empty when nothing in the SDK would show a change; the probe prints the row
beside a new release's added or removed name that matches it, and `test/probe/diff.test.ts` fails
on a name the pinned `sdk.d.ts` does not define. The probe prints the By hand column at the end of every run, as the
checklist of what it cannot see.

The suite replays recorded SDK streams and Slack payloads (`test/fixtures/`), so it cannot see a
change in a new Claude Code CLI: the probe runs the real one. Neither drives the Slack clients, so
how a reply looks on desktop and on mobile is checked by hand.

## Details

Facts about a feature that neither `setup.md` nor `architecture.md` states, kept here so the table stays short.

### A prompt gets one reply

- Two text blocks with no tool call between them (the inner turns of a `/goal`) are written a paragraph apart.

### Thread status

- The status line also goes on an error, besides while an approval or a question waits for you, on `!stop` and when the session closes. It never notifies.

### `!status`

- At the top level, in small text, every thread of the channel that holds a session, live or closed by a restart or an idle hour, newest first by its last message: ten at most, then `+N older, not listed`. Each row is a link to its thread labelled with the session's title (`Session` while it has none), led by the mark its root carries: ⏳ working, ✋ waiting for you, ✅ or ❌ at rest by how its last turn ended.
- A row at rest says how long ago the session's last message was written (`✅ Fix the footer · 16m ago`).
- In a thread, `Title:` follows the `Session:` lines when the agent has one, and the text the thread's first message had before the title ends the message: `Prompt:` and the text as the owner wrote it, in the form the agent receives a message, each line quoted with `> `. A line with no value is left out.

### `!resume`

- A thread that already holds a session, live or only stored in `state.json`, refuses a resume.

### `!open`

- The modal is titled `Open a file`, with the buttons `Close` and `Open`. Its search field is labelled `Search any file`, with the placeholder `Type part of a name`.
- With the field empty, the line above the rows reads `Changed in this session (N), newest first`; with text in it, `N files match`. More than 10 rows say so under them.
- A listing that was cut short adds `The folder could not be listed in full, so some files may be missing here.` An `!open <words>` that finds no match in such a listing answers `No file matching ... was found, but the folder could not be listed in full.`
- An empty file answers `... is empty: there is nothing to show.`
- How long the modal waits for the listing and how the listing is built and kept: [Opening a file](slack-provider.md#opening-a-file) and [Files offered by `!open`](architecture.md#files-offered-by-open).

### Background commands and subagents

- A command left running in the background has no card: its call is counted in its run (`Ran 2 shell commands`), it gets the launch line of every task in the background, the command is a line of the list of what still runs, and its end is one line, `✓ Background command "Wait 40 seconds" completed (exit code 0)`. A command a subagent leaves running is in the list too and has no end line: its end is told to the subagent, whose own end line follows. The same holds for a subagent continued after a restart of the daemon.
- Several tasks started in the background by one message share one launch line, `3 background tasks launched`, with what each does under it as a tree, below the run of that message's calls.
- The list of what still runs counts what is in the background alone, as the terminal's `1 shell still running` does: a command the turn still waits for shows on its own card and is not in it.
- A task's end line is small and grey, as the count of a run of calls is, from its first draw: a stream carries it as the same `context` block the update after the stream's stop writes. It keeps its `✓` or `✗`.
- A report opens with the end lines of the tasks that had ended when Claude Code began that turn. A task that ends after it waits for the turn that reports it, as in the terminal.
- A task Claude Code starts in the background is two lines of the reply's text, in one form whatever its kind (a command, a Monitor, a subagent, a workflow, a kind a later release adds): its name in bold and what it does, `Monitor(ticks)`, then `⎿ Running in background`. The terminal writes such lines for a subagent; the words under the name are the same for every task, and tool-specific details the terminal adds (a Monitor's task id and timeout) are not shown. A subagent is named by its type, `mechanical(Background sleeper)`, and the type `general-purpose` reads `Agent`, as the terminal writes it; any other task by the call that started it. A subagent that runs on another model than the session names it after the description (`Agent(review) Haiku`), and a foreground one ends its card title with `· Haiku`; the launch line waits for the call's result, which carries the model. A task that starts again (a subagent a message continues) gets no second launch line, unless the daemon restarted since it first started.
- A turn Claude Code opens by itself with no task's end to report, such as one a Monitor's event opens, shows Claude Code's text alone: the SDK does not send what woke it (`docs/limits.md`).
- A subagent in the background has no card, and nothing it does shows in the conversation: its calls, the commands it runs, a request of its own that fails. While it runs it is a line of the list of what still runs, its type then what it does, with a second line under it: the call it is at (the words the thread uses for a call), the time that call started or ended and the number of calls it has made. A call of an agent nested in it is not counted. A background command's line has no second line, since the SDK has no public way to read its output while it runs (issue #21). A subagent the call waits for (a skill run in a fork) keeps its card, which counts its calls.
- A subagent's end is one line, `✓ Agent "Background sleeper" finished · 33s`. One that failed says why after the words, `✗ Agent "Background sleeper" failed: Agent terminated early due to an API error: ...`, cut at 400 characters. A subagent that ends while a command it started in the background still runs is waiting, not done, and its line has no mark: `Agent "Background sleeper" is waiting on its own background work · 13s`, then `✓ Agent "Background sleeper" finished · 54s` once it ends for good.
- A background subagent's words are a card under its end, as the terminal's message from it that `ctrl+o` opens: closed on `Message from mechanical`, open on what it said. A report it hands back shows at once, while it still waits on its own work; otherwise its words show once it is done.
- A message that Claude Code took into a report turn is released when that turn ends, and the reply says so at its end: `Claude Code took your message into this reply: send it again if it is not answered here.`
- A message sent while a background task is about to report is answered in a reply of its own, and the report renders into that reply when it is still at rest, or opens a reply of its own at the bottom, since the message sits below the reply that started the task. The two come in the order Claude Code runs the two turns.
- A report renders into the reply that started its task only while that reply is the last thing in the thread. Otherwise it renders into the thread's last reply when that one is at rest (its turn ended and it still waits for a task or a report), under its end line, so a prompt gets as few messages as possible. With a message of yours as the last thing in the thread, or the last reply already ended, the report opens a reply of its own at the bottom. The reply that started the task ends with no report under it, by edit where it is. A reply left behind whose task ends with no report under it is logged.
- A report that comes after the reply that started its task has ended gets a reply of its own at the bottom. The footer of the end it closes is under that report; the footer of an earlier end stays where it was, on the reply above. A footer drawn after a reply ended is an edit and does not notify. Both footers stay after a restart of the daemon between the two.
- A background subagent that hands its report back to the main agent is reported in the reply that started it, while that reply is still open and the last thing in the thread, whether its task's end is told before, during or after the report. The turn Claude Code then gives the task's notification, which does nothing, shows nowhere.

### A restart

- The refusal lists each thread the restart still waits for: its channel, a link labelled with the session's title and what holds it there (`a turn is running`, `an approval or a question is waiting for you`, `2 shells running`, `a background task is about to report, within 30 seconds`). It shows eight rows at most and a count of the rest.
- Under the rows it adds `` `!stop` in a thread ends the wait there. ``, unless every listed thread only waits for a report, which ends by itself.
- `!status` typed in a channel adds, in a message of its own, the rows of that channel's threads and a count of those in other channels, which it does not name.
- The 29-minute limit denies an approval or a question that is still open.
- Closing a session deletes any approval, question or same-folder hold message it denies, not just the ones `!stop` denies.

### Repair after a crash

- The line appended to a repaired reply reads `allaboard stopped before this answer.`
- A question or an approval that opened a turn with no reply is rewritten into that line; a setup form or a hold is deleted.

## Notifications

Every reply, approval request and question is a message inside the session's own thread. The
answer to a word typed in the channel (`!help`, `!guide`, `!status`, `!stop`, `!bind` and its list,
`!resume` and its list, and each refusal), and the upgrade notice, are top-level messages of their
own. A word typed inside a session's thread is answered by an ephemeral message under it (Slack
labels it `Only visible to you`), which disappears when Slack reloads, or by a reaction; `!stop`
is the exception, answered by a message that stays in the thread and can notify. The
old-folder notice and `Not sent.` are ephemeral too. Ephemeral messages did not ring an iPhone
in the two probes of 2026-09-29 that watched for it; one earlier reading did ring and stays
unexplained.

**Inside a thread**, Slack notifies the owner on a new message in a thread it started, mention or
none. Measured 2026-09-28 (Slack free plan, Slack iOS app, slack-sdk 3.44.1):

- a new bot message in a thread the owner started rang, with or without a mention;
- the same message in a thread the owner did not start stayed silent;
- a `chat.update` rewrite never rang;
- a message posted about one second after the owner's own was sometimes not pushed; at 15
  seconds it always was;
- `@channel` does not notify inside a thread (Slack help center, read 2026-09-28).

A reply is a native Slack stream, and a stream notifies in its own way. Measured 2026-09-29 (iPhone
locked, Slack open in a browser, channel on Just mentions, slack-sdk 3.44.1):

- a stream in a thread the owner started pushed once, when it was stopped, with the stream's first
  text as the banner; nothing pushed when it started or while it grew (`mixed-slow` probe: one
  push, reading the reply's first words);
- Slack closes a stream 5 minutes after `chat.startStream`, and an unstopped one pushed at that
  moment;
- after `chat.stopStream`, a `chat.update` of the same message never pushed (`long-one` probe: stop
  at 4 minutes 51 seconds, ten updates, silent), and a new message posted in the thread then did.

Measured 2026-10-13 (desktop client, Slack iOS app, `@slack/web-api` 8.2.0, one run per
condition): with the thread open in front of the owner, a stream's stop did not ring, 47 seconds
after the last new message, and each new message did; the same prompt with the thread closed and
the phone locked rang at the stream's stop as well. Slack's pages for `chat.startStream`,
`chat.stopStream` and `chat.postMessage` say nothing about notifications (read 2026-10-13).

So, inside a thread:

- A reply rings once, when its stream stops, at the end of its turn; a stream's stop stays silent
  while the owner has the thread open. A reply whose turn ends with
  a background command or an agent still running, or still to be reported, stops its stream the
  same way and rests, with no footer: the list of what still runs shows under the
  thread's last reply once it rests, and the message goes on by `chat.update`, silently, until the task
  and its report are done. The footer comes with the end of the whole session, under the reply of
  its latest work, by an edit that does not ring. The banner is the start of Claude's answer.
- A reply that has another reply's message below it ends in the message it is in, by edit, with no
  new post and no ring. So does a reply that rested for background work, has a message of the
  owner's below it and got no text of Claude's since; one still writing its turn when the owner
  writes posts its ending, unless it then rests and gets no text before it ends, and one that got
  a report posts it.
- A reply still open 280 seconds after it started stops its stream then (Slack would close it at
  300 seconds), which rings, and goes on in the same message by `chat.update`, silently. A reply
  that rested has stopped its stream already. Its end
  posts the text Claude wrote after its last call as a new message, which rings a second time
  with the start of that text, and takes the text out of the first message. An answer that is
  text alone keeps it, and the new message holds the footer alone: it is posted once the session
  has ended, and rings then. A turn cut short gets the footer too, with what can be read of the
  session.
  When its reply has no text after the last call to move, the new
  message is the line that says how it ended (`Claude Code reported an error: …`, or
  `This reply ended before an answer: …` after a restart of the daemon), taken out of the
  first message, and the second ring reads that line. When Claude wrote text after its last call, the new message is
  that text with the line under it, and the ring reads the start of the text. No other line
  of the daemon's moves.
- A reply whose stream Slack refuses to grow (`msg_too_long`: Slack does not document its cap, and
  the daemon counts text and cards toward it by measured figures) stops its stream at that moment, which rings, and
  goes on the same way: by `chat.update`, with its ending in a new message. An edit Slack refuses for
  its content is dropped, on any message of a reply: if no later edit of that message passes, the
  reply is short of what Claude wrote and the root shows ❌.
- A reply longer than one message (12,000 characters or 50 blocks, counting each heading, table
  and rule of Claude's text as a block) continues in a new message, and
  each extra message rings. The text of a collapsed diff counts toward the 12,000 in a stream and
  in a post, and not in a message that is edited, which holds up to 45 diffs. Once the reply's end has landed (its stream stopped, its
  ending or its closing message posted), its messages are a fixed set: a late update (a preview,
  a card or words that arrive after the footer) only edits them, never opens a new one. Late
  content is all or nothing: if the last message holds it with everything it showed, it is shown;
  if not, the message keeps what it showed when the end landed and none of the late content
  appears, not even the part that would fit. A late preview of a card that was shown is replaced
  by the note `Preview left out: it did not fit this message.` when a block is free for it; a
  late card or late words that do not fit are left out without one.
- An approval request and a question (`AskUserQuestion`) ring.
- A reply that fails outright (a directory gone missing, untrusted or unreadable, a session
  Claude Code no longer has, or any other exception) ends like any other, ringing once as its
  stream stops; when the whole process exits instead, each open reply's stream is stopped on the
  way out.
- `!stop` and a restart end the reply the same way: the stream stops, and the footer follows by
  an edit on that reply once everything has ended. A restart
  rings once. A `!stop` typed in the thread rings once, and the push shows `Stopped.`, the answer
  posted in the thread: the stream's stop lands within about a second of the owner's own message
  there and did not push on its own (iOS, channel on "Just mentions", one run on 2026-09-29 and
  one on 2026-10-07). A `!stop` typed at the top level is answered in the channel, with
  `Stopped what was running in this channel.`, and sends no push (one run, 2026-10-07). The
  messages a restart dropped from the thread's queue get no reply of their own: they are
  named in the end of the running reply, or in a single message when nothing was running.
- Nothing rings while Claude writes, and a card updating inside the stream does not ring.

**At the top level**, a message rings only under the channel's own notification setting; with
**Just mentions** ([setup](setup.md#create-a-channel-per-project)) it needs a `@channel` mention,
which the daemon writes nowhere. Slack lets a user choose notifications per channel, never per
message, and its reference says nothing about which bot messages notify. Eleven probe messages
sent on 2026-09-27 to an iPhone (Slack iOS app, channel on Just mentions) showed: only a new
message rings, a `chat.update` never does; a mention in the text alone mostly does not; `@here`
reaches only the members Slack counts as active, so it misses an owner who is away.

What is not covered: a second ringing message from the same channel within about a minute of a
first one was silent in most 2026-09-27 probes, which Slack does not document; Android and the
desktop client were not tested.
